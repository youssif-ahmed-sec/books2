# books2 engineering map

- `backend/main.py` mounts the FastAPI v1 routers and serves a complete frontend export, preferring `backend/static` when it contains `index.html` and otherwise using local `frontend/out`. A backend-only release must package the full export into `backend/static`. Deploy to FastAPI Cloud from the `books2` repository root with its Application Directory set to `backend`. `frontend/next.config.ts` sets `output: "export"`; the client calls relative `/api/v1` URLs through `frontend/src/lib/api.ts`.
- Nested Next export routes can request dotted RSC names such as `__next.inventory.product.__PAGE__.txt` while the packaged file lives under nested directories. Keep the fallback mapping in `backend/main.py`; verify both the dotted request and its `.txt` content return 200 when changing static serving.
- Full mode is the default in `backend/core/feature_flags.py` and `frontend/src/lib/warehouseMode.ts`. Set `BOOKS2_WAREHOUSE_ONLY=1` and build with `NEXT_PUBLIC_WAREHOUSE_ONLY=1` only for an explicit warehouse handoff; that mode removes unrelated API routers and gates direct frontend routes. Keep both flags aligned, run `backend/scripts/package_frontend.py` after each frontend production build, then verify the served static export.
- The bookstore currently operates one physical warehouse. In handoff mode, show only counting, and auto-select a warehouse for receiving/counting only when the API returns exactly one active warehouse. If it returns multiple records, require explicit selection; never merge or relabel historical balances by assumption. `/inventory/balances` includes inactive warehouses while `/inventory/warehouses` lists only active ones; counting must reject a product with positive stock in an inactive warehouse until that warehouse is explicitly reconciled. The transfer API is gated to full mode.
- Every nonzero physical count difference requires a reason. An admin's count posts its stock movement and approved audit record in the count transaction without another approval; an inventory controller's count stays pending with no stock change until an admin decides each product separately. Both paths reject stale expected stock. Revision `a62e4d91c8b7` adds sessions and approval fields; verify it on each target before serving count routes.
- Redis caches only role-independent reference lists (categories, subcategories, brands, global units). Mutations through their API routes invalidate after commit; product prices, stock, finance, and role-dependent responses stay uncached. `backend/REDIS_CACHE.md` contains the local Redis setup and external-edit caveat.
- User notifications are private rows in `notifications`, added in the same transaction as purchase, receipt, count, or low-stock events. `/notifications` filters reads and mark-read writes by the authenticated user. All notifications expire seven days after creation; API reads exclude expired rows and a startup/hourly task deletes them from the database. Keep these responses uncached, and mark-read calls must not clear frontend section snapshots. Deploy the notification migration before serving a frontend build with the bell.
- Shift summaries use Gmail SMTP credentials from server environment only; the admin sets the recipient in Settings. Closing a shift snapshots its cash breakdown and recipient before committing, then records SMTP acceptance or failure for admin review and manual retry. Never expose opening, counted, expected cash, differences, or email delivery state to the cashier through shift responses or history; cashiers can still enter opening and closing counts. Revision `c84e7d1a2b30` creates the recipient and report tables; verify each target revision before using these routes.
- The management dashboard refreshes from an admin-only event stream, not an interval. Revision `d35a6f1b8c42` attaches statement triggers to its input tables; PostgreSQL delivers one fixed change signal only after commit. `backend/core/dashboard_events.py` shares one LISTEN connection per API process, and the browser refetches after connecting or receiving a signal. Keep its trigger list aligned with `analytics_service.py` and `dashboards.py` when adding data sources. Apply the migration to a verified target before expecting live updates.
- Main data sections use token-scoped in-memory `sectionSnapshot` values to show their last loaded view while they revalidate on return. Do not snapshot carts, payments, or unsubmitted warehouse/return actions; mutations clear snapshots. The bell's per-user sound switch also controls POS scan and sale cues and local print-submission failure cues. A print-agent HTTP 202 is queue acceptance, not physical print confirmation.
- `backend/models/` contains the SQLAlchemy schema. `backend/api/v1/` contains HTTP handlers; `backend/services/` contains the current order and product write logic. Inspect both layers and their Pydantic schemas before changing a contract.
- `backend/core/dependencies.py` defines role checks. Treat product cost, customer, financial, inventory, and order data as sensitive; verify server side authorization for each affected route rather than relying on frontend role checks.
- Frontend navigation visibility does not guard a direct URL. Protected pages use `frontend/src/components/RoleGate.tsx` through route layouts; keep its allowed roles aligned with the backend dependencies and test a forbidden URL directly in the browser.
- The inventory screen is the frontend visual baseline: shared page surfaces, fields, and buttons live in `frontend/src/app/globals.css` as `app-*` classes, and navigation/login use `BrandMark`. Display monetary values in Egyptian pounds (`ج.م`) and do not present hardcoded sample records or inactive controls as live UI.
- For POS cards, customer forms, or shared visual components, read [references/frontend-design.md](references/frontend-design.md) before editing. It records the verified project hierarchy and review criteria; inspect the current rendered screen as well as the source before applying it.
- Keep the shared `TopNav` on operational screens with search scoped to the current section's records, order follow-up, account actions, and the persisted light/dark theme. Search results should open the record or reveal its row; product selection within sale, receipt, or order forms remains part of those workflows. List searches reuse token-scoped section snapshots; remote catalog and audit searches require explicit submission and stay bounded. Check both themes at narrow and desktop widths when changing shared surfaces.
- Operational roles are `ADMIN`, `INVENTORY_CONTROLLER`, and `CASHIER_ORDERS`. Keep legacy sales enum values in the database for historical rows, but deny their login and existing tokens until an admin explicitly reassigns each account. Cashiers handle order preparation and sales; inventory controllers receive stock. Require an explicit role on user creation, and keep server checks and route layouts aligned.
- The owner does not want a login-attempt limit. Logout revokes only the presented bearer token using its SHA-256 digest in `revoked_access_tokens`; new tokens have a unique `jti`. Apply the revocation-table migration before deploying auth code that checks it. The browser waits for a successful logout response before clearing its token.
- POS customer metrics, expected drawer cash, stock alerts, and management supplier balances aggregate in SQL so checkout and dashboards do not load entire financial histories. Keep exchange orders in net sales but exclude them from original purchase count and last purchase date. Source revision `b7c2e913a4d5` adds customer, shift, and return read indexes; stock aggregation uses the existing unique `(product_id, warehouse_id)` index. Source migration presence is not evidence that a target database has been migrated.
- `/orders` returns a maximum of 100 rows per request with `limit`/`offset`; `group=inbox` and admin-only `group=returnable` filter before paging. The orders, inbox, and returns screens load more in 50-row pages. Keep any new list consumer aware of pagination, while exact invoice lookup remains available for older sales.
- English names for products, categories, subcategories, and brands are optional to enter. Their existing database columns are non-nullable, so an omitted name is stored as an empty string and hidden in the UI; never fill it with the Arabic name as a fabricated translation.
- Supplier management and financial details are admin-only. Inventory controllers may read supplier identity needed by purchase and receiving selectors, but cannot open the supplier section or create, edit, or archive suppliers.
- Warehouse receiving records base-unit quantities only. The `/inventory/receipts` batch commits all lines together under a shared `RCV-` document number, supports safe retries, and never changes product cost or supplier debt. Change product cost in product edit; admin records new supplier debt in the supplier account. Keep direct and purchase-order receiving aligned with this separation, and verify a repeat receipt on an existing balance.
- New multi-line purchases use `purchase_documents`, `purchase_document_lines`, and immutable `purchase_receipts` through `/purchase-documents`; order-line unit conversion factors are captured at request time, warehouse receipt quantities are in base units, and each receipt has a unique request ID. The previous single-product `/purchases` records remain available under `/purchases/legacy` and must not be rewritten or dropped. Apply revision `e6c9a2d4f810` on the verified target before serving the new UI; source migration presence alone is not deployment.
- The sales report and management dashboard are admin-only. The customer section and customer API are for admins and cashiers, not inventory controllers. Inventory controllers can view inventory movement history and counts for stock work. Keep API dependencies and frontend access aligned.
- Supplier balances are opening debt plus historical receipts with `supplier_finance_included=true` plus the net immutable manual debt entries, minus payments. `InventoryService.record_movement` sets the flag false for all new receipts, so warehouse receiving never creates new supplier debt; legacy included receipts retain their original financial effect. `opening_balance` is fixed after creation. Only `ADMIN` may add debt, reverse an entry, or record payment. Cash payment requires an explicit `SHIFT` or `OUTSIDE_SHIFT` source; only `SHIFT` changes the cash drawer. Legacy unpriced or unattributed included receipts keep the balance unknown until reconciled.
- New manual supplier debts require a due date. Historical debt dates stay unknown. The supplier payment UI allocates the entered amount to active debts by earliest due date, then creation time; the API validates exact allocations under a supplier row lock. Any amount beyond open manual debts is confirmed as unallocated against the general balance. Allocations describe settlement and do not alter the supplier balance formula: the full payment reduces the balance once. A debt with allocated payments cannot be reversed. Revision `e52b74c9a610` adds the date and allocation table; verify it on each target before serving these routes.
- `order_items.unit_id` references `product_units.id`. Product edits must preserve existing unit IDs and archive removed units; hard deletion breaks historical orders. Verify a product edit after a sale with foreign keys enforced.
- POS checkout and inventory movements require a client `request_id`; retries with the same ID and payload must return the original result without another stock movement. A reused ID with a different payload must fail. Keep the database uniqueness constraints and concurrency test aligned with this contract.
- Draft order items save bundle component quantities when created. Delivery must consume that snapshot, even if the product recipe changes later; a legacy item without a snapshot needs review before stock can be deducted.
- OMS statuses advance through New Lead, Draft Order, Waiting Quotation, Quotation Sent, Waiting Customer Approval, Approved, Preparing, Ready, Delivered, and Closed. Before delivery, cancellation is allowed; Delivered can only close. The API returns `allowed_next_statuses` so both order views follow the server transition policy. POS creates an already fulfilled order directly.
- Balance mutation and its inventory transaction must be recorded together through `InventoryService.record_movement` in the caller's transaction. The nonnegative database constraint is installed on the primary database.
- Before applying migrations to another database, inspect its revision and inventory balances. The nonnegative migration rejects negative rows; reconcile them only from verified business evidence and transaction history.
- On 2026-10-16 the configured primary production database was read back at Alembic revision `b7c2e913a4d5` after seven additive migrations from its observed `9b7e26c4a19d`. Verify each target's actual revision before deployment; this observation does not establish the state of another target. The existing `ix_sales_returns_order_id` and `ix_payments_shift_id` indexes are preserved by the final migration, which must not drop them on downgrade. Notification and purchase-document tables have row-level security enabled and direct Data API roles revoked.
- `backend/tests/conftest.py` reads `TEST_DATABASE_URL`, then calls `Base.metadata.drop_all()` and `create_all()` at setup and `drop_all()` at teardown. Run these tests only after verifying the URL points to an isolated disposable database. Never assume the presence of `TEST_DATABASE_URL` alone proves isolation.
- Supabase Root 2021 CA lacks a key-usage extension rejected by Python 3.13+ `VERIFY_X509_STRICT`. For Supabase hosts, `backend/database.py` uses the bundled `backend/certs/supabase-root-2021.crt` when `DATABASE_SSL_CA_CERT` is unset and clears only that strict flag; certificate-chain and hostname checks remain enabled. A custom CA path still needs `DATABASE_SSL_ALLOW_LEGACY_CA=1` when it uses this legacy provider CA. Verify the target identity read-only before database tests or migrations.
- `backend/alembic/` holds migration source; distinguish it from the schema actually applied to any database. Inspect migration operations before running Alembic because the initial revision contains a table drop and alterations to preexisting tables. The receipt snapshot revision depends on that initial revision; do not run `upgrade head` until the target's existing schema and revision state are verified.
- `print_agent/` is a separate Windows localhost service that receives receipt jobs and controls native printers. Check the browser to localhost boundary and actual printing behavior before changing it.
- All invoice, receipt, and barcode print actions send structured jobs to the local print agent; quotations are view-only and have no print action. No frontend route should call browser printing. The agent queues jobs with HTTP 202, which is not proof that a physical printer completed them. Rebuild `print_agent/dist/SouodElShafiePrintAgent.exe` after changing its renderer.
- Barcode print jobs use each saved unit barcode. Add-product Save and Print lets the operator select units and defaults copies from entered unit stock; the local agent accepts at most 20 copies per queued job, so the browser sends larger counts in chunks. `print_agent/print_agent/printer.py` renders a compact Code 128 label with store, product/unit, code, and price. Validate its image and API rejection path; a successful 202 confirms queueing only, so verify the real printer separately.
- A saved product or unit barcode cannot be changed. A previously blank barcode and a new unit can receive a code once; archiving a unit keeps its barcode reserved. Enforce this in `ProductService.update_product` as well as the edit form.
- Offers use `product_bundle_components.quantity` in base units for inventory deduction; `unit_id` and `price_level` remember each selected product's unit and price tier. The dedicated `/offers` API and page create bundles from existing products and save one final sale price across all customer tiers. Inventory controllers may create offers; only admins may edit, activate, deactivate, or delete them. Offer products do not get opening stock or enter purchase orders or direct receipts. The offers page is available in warehouse handoff mode, while sales routes remain paused.
- WhatsApp webhook verification needs `WHATSAPP_VERIFY_TOKEN` and signed POST delivery needs `WHATSAPP_APP_SECRET`; the handler fails closed when either is absent. Deployed browser printing needs its exact origin in `PRINT_AGENT_ALLOWED_ORIGINS` on the local agent.
- WhatsApp webhook and automated Business Platform messaging remain outside the current launch scope: `WHATSAPP_ENABLED` defaults off and its endpoints return 404. Even when enabled, signed inbound messages return 503 until a durable lead and reply workflow is implemented; never acknowledge an unhandled message with 200.
- Purchase-order WhatsApp drafts are an admin-only click-to-chat flow at `/integrations/whatsapp`: the admin reviews the message inside the ERP, opens the supplier chat through `wa.me`, and sends from WhatsApp Web. Opening a draft is not proof of delivery. This flow does not enable inbound webhooks or automatic Business Platform sending.

Do not copy environment values into reports or instructions. Check the current Git status before editing; generated Python cache files have been tracked in this repository. `backend/.env` is currently untracked and ignored, but contains sensitive local configuration.
