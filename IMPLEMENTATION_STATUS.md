## Warehouse handoff candidate (local source, 2026-10-10)

Current local source (2026-10-16): full mode is the default in both layers. Warehouse handoff now requires explicit `BOOKS2_WAREHOUSE_ONLY=1` and a frontend build with `NEXT_PUBLIC_WAREHOUSE_ONLY=1`. The local full-mode frontend export was rebuilt and packaged into `backend/static`; this does not deploy the application or change the production database. Physical printing remains to be checked on the client's device.

At the 2026-10-10 handoff, warehouse-only mode was enabled by default in both layers. The API kept authentication, product/catalog data, inventory, suppliers, purchases, stock alerts, and audit available; unrelated sales, POS, customers, finance, returns, and messaging endpoints were not mounted. Supplier payments returned 404 in that mode. The frontend showed only warehouse work and sent direct visits to paused pages to `/paused`. This paragraph describes that historical handoff; the current local mode is stated above.

Adding a product now offers `حفظ فقط` and `حفظ وطباعة باركود واحد`. The latter queues one label after the product saves and uses the saved barcode/SKU; it does not derive label count from opening stock. The local print agent validates the code and copy count before accepting a barcode job, and renders Code 128 without resizing its bars. `docs/barcode-label-preview.png` is a sample generated by that same renderer; its example value is not a real inventory code.

Verification for this candidate: 54 existing unit tests passed with full mode enabled; 7 existing API/integration tests passed with full mode enabled; 10 warehouse-mode unit tests passed; 2 warehouse handoff integration journeys passed twice against the isolated disposable database; 12 print-label tests passed. The handoff journeys cover roles and anonymous requests, idempotent and partial receipts, transfers, counts, stock alerts, concurrent last-unit issue, ledger consistency, audit, product archive guards, and supplier-payment shutdown. The isolated database had zero public tables after teardown. The frontend production build passed, and `backend/scripts/package_frontend.py` verified 230 exported files in `backend/static`. A temporary backend browser check confirmed `/paused` and direct `/orders` routing to it. The Windows print agent was rebuilt into `print_agent/dist/SouodElShafiePrintAgent.exe`; the packaged executable passed local health and browser-origin checks (unknown origin 403, allowed development preflight 200). The primary database was not changed in this handoff pass. Physical printing and the deployed environment still require checks on the client's device.

## Local security and performance review (2026-10-16)

Auth logout now revokes the presented token after recording only its hash; the cashier still has no login-attempt limit, as requested. POS product search and order lists are bounded. Orders, inbox, and returnable invoices use 50-row pages, with server-side status filtering before pagination; the cashier cannot request the returnable invoice list. The unused conversation count route is admin-only, and cashier preparation queries filter the assignee in SQL. Customer purchase metrics, expected cash, stock alerts, and management supplier finance use database aggregation. The final isolated unit runs passed: 91 in full mode and 10 in warehouse-only mode, which must run separately because route registration is fixed at import time. The local frontend passed ESLint, TypeScript, and a 28-route production build; 284 static files were packaged into `backend/static`. A disposable localhost fixture confirmed order list loading from 50 to 100 rows, inbox load-more, and narrow light/dark layouts for the order and return screens. Source migrations `f8c1e2a3d4b5`, `a19d6b7c8e20`, and `b7c2e913a4d5` are pending on any target database; no production database or deployed application was changed in this review. Physical printer verification remains deferred.
